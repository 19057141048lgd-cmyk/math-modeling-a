# 数学建模 A 题：通用神经网络处理器下的多核调度

这个仓库给队友接着做。先看设计文档，再按下面的目录找代码、正式结果和实验原始记录。

## 先看这个

[A题方案/A题方案设计.md](A题方案/A题方案设计.md)

里面有题目机制、三个小问的建模和算法、正确性说明、16 个代表用例和全部 100 个用例的结果、模型哪里不准、还没做完的实验、按性价比排好的改进，以及运行命令。

## 做法

三个小问共用一套框架：两级粗化，通信感知列表调度，代理模型（算子级调度模型 + 精确 spill 模型）选优，需要时再交官方评估器复核。差别只在代价模型和方案怎么构造。

全量 100 个用例、只用模型选优时，5 核平均加速比是：问题1 **3.76**，问题2 **4.32**，问题3 **4.43**。这是模型选优后的官方成绩，不是候选中经官方验证的最优；单核加速比按题目定义为 1；随核数单调不增是靠兜底比较保证的。口径和分项都在设计文档第 0 节、第 7.4 节，原始数字以 `A题方案/results_all/summary.csv` 为准。

## 接着做时先看这些问题

完整排序在设计文档第 8 节。下面这些会直接影响下一步：

1. 问题1 的代理模型偏乐观。全量结果平均偏低 4.9%，484 个组合里有 101 个低估超过 10%。只用模型选优时，可能错过更好的切分或朴素基线。
2. case_035 的问题2 被严重低估。4 核、5 核预测是 58356 / 52098，官方是 96489 / 91346。原因还要对官方 trace。
3. 大图内存还没解决。case_014（约 3.57 万个计算算子）在问题2、4 核时，9 个候选都有 52–60 MB spill，问题2 的 makespan 只和问题1 持平。把切段放大或缩小几乎不改变 spill。可以做的是：同核上把共用同一批输入的簇排在一起，或者选核打分时直接加上 spill 模型给出的增量。spill 字节已经和官方逐字节一致，这一步不必每次调用官方评估器。
4. 问题2 的 5 核方案里仍有 27 个用例带 spill。
5. case_016、case_024、case_051 会触发粒度自适应。case_051 在 3 核上模型选错了，加速比从 2.24 降到 2.16。
6. 设计文档 7.5 节列出的实验还没补齐：100 个用例的官方复核、100 个用例的朴素基线，以及消融（去掉 in-tree 聚簇、去掉局部性惩罚、问题2 改成粗切段、问题1 去掉 Task 规模族）。

## 怎么跑

在 `A题方案` 目录下执行。Python 3.10 及以上，求解只用标准库，画图需要 matplotlib。官方附件由 `solver/config.py` 自动定位。

```powershell
python -m solver.solve case_050 --cores 4 --problem 2 --verify 2 -o results/case_050_p2_n4.json
python -m solver.run_batch --cases all --verify 0 --workers 8 --out results_all
python -m solver.dev_spill results_all
```

`run_batch` 中断后用同一条命令重跑，只会补未完成的用例。其余命令、参数和论文分工在设计文档第 9、10 节。
